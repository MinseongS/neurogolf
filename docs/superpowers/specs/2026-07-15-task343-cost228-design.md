# task343 Cost-228 Design

## Goal and acceptance criteria

Reduce the live task343 model from cost 252 to cost at most 228 without touching any
other task. A candidate is eligible for adoption only when all of the following hold:

- precomputed cost is at most 228;
- bundled evaluation has zero failures;
- fresh generation completes at least 1500 cases with candidate failure zero and
  deployed-versus-candidate divergence zero;
- the official sequence is `ng gate` followed by `ng adopt`;
- adoption is never simulated with a manual manifest or deployed-file edit.

The pinned environment remains `onnx==1.21.0` and `onnxruntime==1.26.0`. The current
cost-252 deployed graph and its exact source are the immutable comparison baseline.

## Considered approaches

### 1. Predicate fold plus one-row signature — falsified

First make an exact control that preserves the three-row base-10 signature while
reducing predicate overhead. The p3 branch will choose a vector of values 3 or 4 and
`ReduceMax` it, so any unequal signature selects 4. The p4 and visibility predicates
will remain rank-4 singleton tensors through the nested `Where` nodes; a single final
`Squeeze` will replace the current three predicate squeezes. These two folds are exact
for every input and are expected to reduce cost 252 to 248.

Changing the shared signature kernel from three rows to the bottom row reduced the
measured graph to cost 228, but bundled evaluation rejected it at 261/266. All five
failures were period-6 cases whose bottom colour was constant across the six base
columns, so the p4 predicate necessarily misclassified them as period 4. Exhaustive
single-row, mixed-row, and independently placed scalar-probe simulations did not beat
five failures. This representation is retained only as a negative control.

### 2. Smaller dynamic terminal indices — rejected for this iteration

The 120-byte `final_cols` tensor is the largest counted object. ONNX `Gather` under the
pinned checker/runtime requires int32 or int64 indices, and the output needs all 30
positions, including the padding half. No legal narrower index dtype or terminal
operator has been identified. This path is reopened only by a concrete legal operator
whose full graph prices at 228 or below.

### 3. Exact factorization of the three-row signature — rejected for this iteration

The signature weights are an outer product of ten colour codes and three row weights.
Materializing either factor at runtime introduces counted intermediate tensors larger
than the 20 parameters saved. Pooling alternatives lose row order. This path is not
built unless a factorization with no wider runtime basis materialization is found.

### 4. Sparse initializers — structurally rejected

A scalar-p3 design combined with sparse kernel/index initializers priced at 228 in the
scorer model, but ONNX 1.21 full shape inference rejects both sparse Conv weights and a
sparse Mod operand as unsupported sparse tensor types. Minimal isolated probes reproduce
the same schema failure. This route is structurally unavailable under the pinned
checker/runtime and was not gated or adopted.

### 5. Joint low-period predicate — selected and adopted

The final design keeps exact three-row signatures but removes the entire 31-byte p3
subsystem. The existing p4 equality `col4==col0` is shared with one new equality
`col5==col1`. For visible width at most8, their conjunction selects period4; otherwise
period3. Generated n=4 patterns always satisfy both equalities. For n=3, both can hold
only when the three signature classes collapse to the same effective repeated pattern,
so selecting period4 instead of3 does not change the output.

Two exact shaves remove four parameters: visibility uses float-to-bool Cast with swapped
Where branches instead of a zero initializer, and attribute-axes ReduceMax replaces the
parameterized final Squeeze. The resulting graph has six scalar Conv probes, memory160,
params64, and cost224. It passed bundled266/266, a 10,000-case generator simulation,
fresh1500 deployed A/B with fail0/divergence0, and the mandatory gate/adopt sequence.

## Components and data flow

Four independent candidate builders live under `candidates/task343/`:

1. The exact predicate-fold control consumes the current exact-signature builder,
   rewrites only the p3/p4/visibility decision nodes, infers shapes strictly, and saves
   a cost-248 ONNX graph.
2. The falsified one-row builder consumes that control and replaces the signature
   kernel and negative top padding so every probe reads row 4 only.
3. The rejected sparse prototype established that sparse Conv/Mod operands fail pinned
   full shape inference; its temporary artifacts were removed.
4. The selected cost-224 builder retains scalar probes at columns 0,1,4,5,8,11, shares
   the p4 equality with the low-period decision, folds visibility and singleton handling,
   and leaves terminal `Mod(fmod=1)` plus `Gather(axis=3)` unchanged.

The cost-248 control passed 266/266. The one-row candidate's five failures and the sparse
schema rejection are recorded as dated negatives. Only the joint low-period candidate
continued to fresh validation and adoption.

## Validation and failure handling

Tests are written before builders. They assert node topology, shapes, initializers,
predicted cost, and the intended row-specific Conv padding. Each test must first fail
because its builder or candidate is absent, then pass after the minimal implementation.

Validation proceeds in this order:

1. Run the focused incumbent tests.
2. Build and statically price the exact control; require cost 248.
3. Evaluate the control on all bundled examples; require zero failures.
4. Preserve the one-row candidate as a cost-228/fail-5 negative control.
5. Build the joint predicate candidate; require strict checking, memory160, params64,
   cost224, and bundled zero failures.
6. Run 1500 fresh generated examples against the deployed model; require candidate
   failure zero, incumbent failure zero, and divergence zero.
7. Run `ng gate`; only on success run `ng adopt`, then regenerate exact source and
   re-run the focused suite and `ng score 343`.

Any mismatch, checker/runtime error, cost above 228, bundled failure, incomplete fresh
run, or fresh divergence terminates the adoption path. No manifest edit, deployment
copy, wider runtime basis, cost-684 recovery, or other-task work is permitted.
